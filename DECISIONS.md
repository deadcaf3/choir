# Decision register

Code comments across this workspace cite decisions by number (`D6`, `D29`,
`D41`). This table is what those numbers mean.

Each row records **what** was decided and whether it is a **one-way door** — a
choice that is a data migration to reverse rather than a refactor. One-way rows
are the ones to read before changing anything a comment tags.

The rationale behind each decision, the fallback chosen for it, and the tripwire
that would reverse it are not published.

| D61 | Export/import is a *format* tool in the daemon binary, not a second deployment script. `--export <root> <dir>` writes the op log, a git bundle per repository and a versioned manifest; `--verify-export <dir>` settles what that directory claims by folding the log and requiring every ref the view names to be in a bundle at the same oid; `--import <dir> <root>` places one into a fresh root, refusing a root that already holds a log or a named repository, and leaves proving it to the boot that accepts a write. The plan's §E standing rule asks for this and `scripts/pull_backup.sh` does not satisfy it: that script pulls over ssh from a fixed remote path, refuses to run on the machine holding the log, takes its repository list from a policy file, needs python3 to project a hash, and checks bundles against the D25 attestation rather than the log. All of that is right for recovering one deployment and none of it travels, so the script keeps its transport and this owns the format. The check runs in one direction on purpose -- a bundle may be ahead of the log, a log may never name a commit no bundle holds -- which is what makes exporting a running node meaningful, since the log is read before the bundles are taken; the benign direction is counted and reported rather than hidden. Secrets are excluded by copying four names and then walking the finished directory and refusing anything whose name has the shape of one, so the guarantee is a property of the output. Reversal costs nothing to third parties, which is the property being bought: an export nobody can read with our code is still a jsonl log and a set of git bundles | Two-way |

| D64 | Phase 1's absolute targets become measurements that can fail, and each is measured as the thing it can honestly be. The plan names four -- 5 commits/s/repo through the queue, green-keeping at 50 in-flight, 10k clones/hr, read p99 under 100 ms in-region -- and measured none: `choir-spike` is the *Phase-0* gate, `throughput.rs` reports the write path and deliberately asserts nothing, and nothing looked at reads at all. An unset gate is not a passed gate, which is the rule the withdrawn adoption criterion is already written down under; these had less excuse, because they existed and only needed instrumenting. Four interpretations are the substance. **5 commits/s/repo is measured as the queue's own cost against the 200 ms per change that rate implies**, not as end-to-end commits/s: CI is a caller-supplied verdict (D18) and a synthetic runner returns instantly, so an end-to-end figure with fake CI would measure the fake; the useful number is what is left for CI, and it is 199.8 ms of 200. **Clones are measured concurrently**, because 10k/hr is 2.8/s and one client would clear that without the server ever being the constraint; concurrent, they run at ~14/s (~50k/hr) and do not serialize behind `git http-backend`. **"In-region" cannot be represented on loopback**, so the read figure is the service-time floor and is reported as one. It was first taken by shelling out to `curl` per sample, counting the spawn as rough compensation for the missing wire; the spawn turned out to *be* the measurement. Timed directly over a `TcpStream`, `/api/view` reads p99 306 us, against p99 11 ms idle and 155 ms under a gate with a `curl` fork in front of it -- about 99.8% of the figure was process spawn on a busy machine. Every read number taken before that correction, including ones cited in this row, was a measurement of fork/exec with a node attached. **The git-backed pages are gated on subprocess count, not on the stopwatch.** The repository front page measured p99 94 ms and p99 246 ms an hour apart on one commit, the second time with a toolchain build on the machine; a tripwire that fires on the weather gets disabled, which is worse than not having one. Most of that swing was the sampler's own `curl` spawn and is gone now, but the conclusion is kept because the reasoning was right for a second reason: a page whose cost is eight subprocesses is timing the operating system's scheduler as much as the node. So `phase1_spawns.rs` budgets the git spawns the latency is made of -- ~10 ms each here, 8 for the front page and 3 for a forty-file directory -- the way `alloc_budget.rs` budgets allocations, and the wall-clock file reports the target and asserts only that a page has not hung. The loose ceiling was tried first and is worth recording as a mistake: 600 ms, picked as "loose enough to survive a loaded machine", failed a healthy tree on its first full gate at p99 748 ms with a parallel release suite running. A bigger number would have been the same mistake with a longer fuse, so the wall-clock assertion on those pages went away entirely and the spawn budget carries them alone. **What the front page actually costs, corrected.** It was recorded here as missing the 100 ms target outright, at ~90 ms p99 idle and worse under load. With the sampler no longer forking per sample it reads p99 70 ms and p99 111 ms in two runs at load averages 14 and 18 -- close to the target rather than far over it, and whether it meets it depends on the machine. Two spawns came out along the way: the listing's dates, which were one `git log` per row, and a second read of `refs/heads/` that every render did because naming `HEAD` and filling the ref picker each asked git separately. Nine spawns, then eight. The report line still prints `meets` or `OVER` per run rather than resolving it in prose. A fifth Phase-1 number joins them for the same reason the four did: complete-view growth had live readings taken by hand from a node that no longer exists, and no test that could fail. The claim worth gating is not a byte count but a shape -- the authoritative view is a function of what is live now, not of how long the node has run -- so two hundred create/delete cycles must leave the total exactly where it started, and fifty live refs must cost fifty times one. Both halves are needed: a total that never moves passes the first and is just as broken. Byte counts rather than a stopwatch, so it runs in the merged harness. The cause is spawns, so the fix is fewer of them; one already landed, the listing's dates going from a `git log` per row to one walk for the whole listing, worth ~20 ms on the front page | Two-way |
| D65 | The vouch: one operator's sequenced statement that it stands behind another, as `OpKind::Vouch`/`OpKind::WithdrawVouch` folding into `View::vouches` (subject -> voucher -> `{at, note}`). This is the second of D24's four T1 inputs to exist. Key age was the first, and age alone cannot tell a hundred keys one stranger bound from a hundred keys a hundred operators bound, because age is a fact about a key and never about anybody's opinion of it. **The Sybil floor is in the fold, not the daemon**: both ends must be operators holding an unrevoked `BindKey`, so an edge minted from nothing is refused by every replayer rather than by one node's private admission rule -- and since `BindKey` is node-only (D24), an attacker cannot mint the identity a fresh vouch would come from. The same rule bounds the map to one edge per ordered pair of operators the node itself admitted, which is how a client-writable section stays inside D64's growth property. Self-vouching is refused, and so is spelling an end as a channel: `ana` and `ana/agent` are one operator, and admitting both would give it two rows and a path to itself in two hops. One edge per pair makes the pair a retry identity, exactly as a comment id is for D38, so a resubmission after a lost response cannot silently redate an endorsement. `voucher` is payload data the fold cannot check -- it is handed an op, never a signer -- so admission binds it to the **operator prefix** of the signing channel, the D55 rule one level up; unchecked, the graph would be an attacker's document rather than a record. It needs node-wide *read* and not write: a vouch names no repository, so write would mean the web of trust is authorable only by identities that can already move any ref, which is not a web. **Withdrawal removes the row.** The log keeps both ops, so a current view answers "who vouches for X now" and "who used to" is a question for the log -- the split `DeleteRef` already makes. The cost is real and is not hidden: a reader of a current view cannot tell "never vouched" from "vouched and withdrew", which is a signal worth having. It is paid because the alternatives are worse -- a tombstone either makes withdrawal terminal, which trust is not, or is overwritten by the next vouch, leaving a row that says nothing -- and because vouch churn then cannot grow the view. Withdrawal is deliberately exempt from the bound-operator floor: whoever holds a key after a compromise needs the edge gone at exactly the moment that operator has no live key left. **A vouch authorizes nothing.** No threshold reads it, no score is computed, and admission is unchanged -- a fresh registered key is still admitted on registration alone, which is now a stronger statement than when there was no graph to consult. Two inputs are not more scoreable than one: any weighting of age against endorsements is a claim nobody here has measured, and a number would read as that measurement while being a guess. Reciprocity is surfaced instead, as a fact and not a verdict, because a mutual edge is the shape a Sybil farm makes and also the shape a real team makes. The profile and `/p/<channel>` read the graph operator-scoped and say so in the heading, since a page about `ops/agent` is showing what was vouched to `ops`. Section disclosure is `NodeWide` like `bindings`: a reader granted one repository gets a profile that is byte-identical to an unknown actor's, so the graph is not readable through the shape of a refusal. Measured beside `bindings` in `view_growth` and deliberately outside `total_authoritative_view`, which is a tracked series a fifth section would silently rewrite. Fixed on the way: `/api/profile?channel=` decoded its value as a path segment, so every agent channel -- the ordinary shape here -- answered 400 while its page rendered. Scoped grants are absent here and arrived as D66 as a *time-lock on an ACL grant*, which is a mechanism and not the log-visible T1 input D24 asks for; bonds are still absent, as are decay and the vouch-graph-distance conflict-of-interest constraint on reviewer assignment, and all of them are named rather than implied. The shape follows the Sybil research rather than the folk version of a web of trust: the per-attack-edge bounds in the SybilGuard/SybilLimit line are a function of how many honest-to-Sybil edges an attacker can form, which is the wrong assumption when the work that earns an edge is free, so resistance stays anchored at the operator level and the graph is not even an accelerator. Showing only the immediate circle is the attenuation that literature argues for. ## Reading the door column

- **Two-way** — reversible by deleting code. No persisted format, op, hash or
  signature is involved, so reversing leaves nothing to migrate.
- **One-way** — the choice is baked into bytes that already exist. Reversing it
  means migrating persisted data.
- **One-way for readers** — the feature can stop being *written* at any time and
  nothing breaks, but the log is append-only, so the first accepted entry of
  that shape permanently ends replay compatibility with earlier binaries.
- **Gated** — deliberately deferred, with the swap planned rather than assumed.
