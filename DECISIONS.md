# Decision register

Code comments across this workspace cite decisions by number (`D6`, `D29`,
`D41`). This table is what those numbers mean.

Each row records **what** was decided and whether it is a **one-way door** — a
choice that is a data migration to reverse rather than a refactor. One-way rows
are the ones to read before changing anything a comment tags.

The rationale behind each decision, the fallback chosen for it, and the tripwire
that would reverse it are not published.

| D59 | The deployment handles no client address. The proxy writes no access log, keeps no per-address rate or connection zone, discards its error log, and clears `X-Forwarded-For` rather than appending to it, so nothing downstream can read one; the record that survives is the node's own request log, which never had an address field to drop. | D60 | A `propose` grant, ranked between `read` and `write`: it admits a push to `refs/for/<branch>/<user>/<topic>` (D53), where the pusher's own name is a required segment because several people hold this grant at once and it is what keeps them from reaching one another's proposals, and refuses every other ref, so a repository can take a contribution from somebody who is not trusted with its branches. | D61 | Export/import is a *format* tool in the daemon binary, not a second deployment script. `--export <root> <dir>` writes the op log, a git bundle per repository and a versioned manifest; `--verify-export <dir>` settles what that directory claims by folding the log and requiring every ref the view names to be in a bundle at the same oid; `--import <dir> <root>` places one into a fresh root, refusing a root that already holds a log or a named repository, and leaves proving it to the boot that accepts a write. The plan's §E standing rule asks for this and `scripts/pull_backup.sh` does not satisfy it: that script pulls over ssh from a fixed remote path, refuses to run on the machine holding the log, takes its repository list from a policy file, needs python3 to project a hash, and checks bundles against the D25 attestation rather than the log. All of that is right for recovering one deployment and none of it travels, so the script keeps its transport and this owns the format. The check runs in one direction on purpose -- a bundle may be ahead of the log, a log may never name a commit no bundle holds -- which is what makes exporting a running node meaningful, since the log is read before the bundles are taken; the benign direction is counted and reported rather than hidden. Secrets are excluded by copying four names and then walking the finished directory and refusing anything whose name has the shape of one, so the guarantee is a property of the output. Reversal costs nothing to third parties, which is the property being bought: an export nobody can read with our code is still a jsonl log and a set of git bundles | Two-way |
| D62 | Search gets an agent surface: `GET /api/search` and `choir search`, node-wide by default across every repository the caller may read, each at its own `HEAD`. D30 shipped search as a page and only a page, on a platform whose primary reader cannot open a browser -- the one caller most likely to ask "where is this symbol" had no way to ask. It reuses the page's own three functions against the same resolved oid, so the two surfaces cannot disagree about what a match is, and it sits ahead of the platform API in the router for the reason the account endpoints do: it reads git and needs no sequencer, so a node serving nothing but repositories can still answer. Three choices are the substance. **One scope per request, not three**: the page runs all three because its tabs carry counts and a reader landing on an empty tab concludes the search is broken, but a caller named the scope it wanted and node-wide the difference is `3n` git invocations rather than `n`. **A repository the caller was not granted is answered exactly as one that does not exist**, because learning that something exists is itself the leak; the grant is applied inside the repository walk the index page already uses, so no caller can enumerate what it may not read by forgetting to filter, and a `repo=` that fails to parse is refused rather than treated as absent -- parsed at the query-string layer it silently widened a question about one repository into an answer about all of them. **No index.** It is one `git grep` per repository, unbounded in the number of repositories, and that is the honest shape of it: a trigram index is what answers a measurement saying this is too slow, and no such measurement exists. Reversal is adding an index behind the same response, which is why this is two-way; what would be hard to reverse is the response shape, so `matches` counts everything found while `limit` bounds what comes back and `truncated` says which happened | Two-way |
| D63 | Profiles are a *reading* of the view, not new state: `GET /api/profile?channel=X` and a `/p/<channel>` page counting one actor's bound keys and their age, changes owned, reviews assigned, verdicts given, approvals slashed, comments written and checks reported. D24's Sybil resistance wants key age, vouches, scoped privilege grants and bonds; only key age is persisted, as `KeyBinding::bound_at`, so the page reports that input and says plainly that the other three do not exist -- `vouches` is present and null rather than absent, because a reader who finds no vouches should learn there are none to find. | D64 | Phase 1's absolute targets become measurements that can fail, and each is measured as the thing it can honestly be. The plan names four -- 5 commits/s/repo through the queue, green-keeping at 50 in-flight, 10k clones/hr, read p99 under 100 ms in-region -- and measured none: `choir-spike` is the *Phase-0* gate, `throughput.rs` reports the write path and deliberately asserts nothing, and nothing looked at reads at all. An unset gate is not a passed gate, which is the rule the withdrawn adoption criterion is already written down under; these had less excuse, because they existed and only needed instrumenting. Four interpretations are the substance. **5 commits/s/repo is measured as the queue's own cost against the 200 ms per change that rate implies**, not as end-to-end commits/s: CI is a caller-supplied verdict (D18) and a synthetic runner returns instantly, so an end-to-end figure with fake CI would measure the fake; the useful number is what is left for CI, and it is 199.8 ms of 200. **Clones are measured concurrently**, because 10k/hr is 2.8/s and one client would clear that without the server ever being the constraint; concurrent, they run at ~14/s (~50k/hr) and do not serialize behind `git http-backend`. **"In-region" cannot be represented on loopback**, so the read figure is the service-time floor and is reported as one. It was first taken by shelling out to `curl` per sample, counting the spawn as rough compensation for the missing wire; the spawn turned out to *be* the measurement. Timed directly over a `TcpStream`, `/api/view` reads p99 306 us, against p99 11 ms idle and 155 ms under a gate with a `curl` fork in front of it -- about 99.8% of the figure was process spawn on a busy machine. Every read number taken before that correction, including ones cited in this row, was a measurement of fork/exec with a node attached. **The git-backed pages are gated on subprocess count, not on the stopwatch.** The repository front page measured p99 94 ms and p99 246 ms an hour apart on one commit, the second time with a toolchain build on the machine; a tripwire that fires on the weather gets disabled, which is worse than not having one. Most of that swing was the sampler's own `curl` spawn and is gone now, but the conclusion is kept because the reasoning was right for a second reason: a page whose cost is eight subprocesses is timing the operating system's scheduler as much as the node. So `phase1_spawns.rs` budgets the git spawns the latency is made of -- ~10 ms each here, 8 for the front page and 3 for a forty-file directory -- the way `alloc_budget.rs` budgets allocations, and the wall-clock file reports the target and asserts only that a page has not hung. The loose ceiling was tried first and is worth recording as a mistake: 600 ms, picked as "loose enough to survive a loaded machine", failed a healthy tree on its first full gate at p99 748 ms with a parallel release suite running. A bigger number would have been the same mistake with a longer fuse, so the wall-clock assertion on those pages went away entirely and the spawn budget carries them alone. **What the front page actually costs, corrected.** It was recorded here as missing the 100 ms target outright, at ~90 ms p99 idle and worse under load. With the sampler no longer forking per sample it reads p99 70 ms and p99 111 ms in two runs at load averages 14 and 18 -- close to the target rather than far over it, and whether it meets it depends on the machine. Two spawns came out along the way: the listing's dates, which were one `git log` per row, and a second read of `refs/heads/` that every render did because naming `HEAD` and filling the ref picker each asked git separately. Nine spawns, then eight. The report line still prints `meets` or `OVER` per run rather than resolving it in prose. A fifth Phase-1 number joins them for the same reason the four did: complete-view growth had live readings taken by hand from a node that no longer exists, and no test that could fail. The claim worth gating is not a byte count but a shape -- the authoritative view is a function of what is live now, not of how long the node has run -- so two hundred create/delete cycles must leave the total exactly where it started, and fifty live refs must cost fifty times one. Both halves are needed: a total that never moves passes the first and is just as broken. Byte counts rather than a stopwatch, so it runs in the merged harness. The cause is spawns, so the fix is fewer of them; one already landed, the listing's dates going from a `git log` per row to one walk for the whole listing, worth ~20 ms on the front page | Two-way |

## Reading the door column

- **Two-way** — reversible by deleting code. No persisted format, op, hash or
  signature is involved, so reversing leaves nothing to migrate.
- **One-way** — the choice is baked into bytes that already exist. Reversing it
  means migrating persisted data.
- **One-way for readers** — the feature can stop being *written* at any time and
  nothing breaks, but the log is append-only, so the first accepted entry of
  that shape permanently ends replay compatibility with earlier binaries.
- **Gated** — deliberately deferred, with the swap planned rather than assumed.
