# Decision register

Code comments across this workspace cite decisions by number (`D6`, `D29`,
`D41`). This table is what those numbers mean.

Each row records **what** was decided and whether it is a **one-way door** — a
choice that is a data migration to reverse rather than a refactor. One-way rows
are the ones to read before changing anything a comment tags.

The rationale behind each decision, the fallback chosen for it, and the tripwire
that would reverse it are not published.

| D5 | Speculative merge queue with a TCP-like window. **The merge step is a seam, `speculate::Speculator`, and the queue's states are opaque strings** -- the window that grows by one and halves on failure, the dependency-aware blast radius, the refusal to land one change twice and the rule that only a real test failure evicts anybody are none of them statements about text. They were written against text anyway, because the queue called `choir_merge::Pipeline` directly and a `Change` carried two file bodies, so nothing holding a repository could construct one. The consequence was structural rather than cosmetic: the queue was composed into nothing, and every number its tests reported was a simulation of a train rather than a train. `TextSpeculator` is the extracted original and `GitSpeculator` is the second implementation, where a state is a commit id and a merge is `git merge --no-ff` in a worktree it owns. **A state stays a `String`**, which is why this needed no generic parameter and no change to `Change`: the queue moves states around and never looks inside one. Three things move behind the seam with it, each because git answers differently. The **merge**, obviously. The **identity**, because a rebased resubmission must be recognized and git's answer is a patch id rather than a normalized diff -- computed with `-U0`, since a three-line file rebased onto a change to its last line has different context for the same edit, so keeping context would break identity in exactly the case it exists for. And the **subject**, because a check recorded against `blake3(oid-text)` names a tree no git client can resolve; `GitSpeculator` names its states with the git codec, which is the same hash the landing records as the workspace head. A fourth `Step` case, `Unavailable`, arrives with git: a merge that could not run is not a conflict, and blaming an author for our own broken worktree is the mistake D18's four verdicts exist to prevent one level up. The queue stalls on it exactly as it stalls on a provider fault -- everything requeued in order, nobody evicted, the window untouched -- and the distinction is drawn on `MERGE_HEAD` existing rather than on git's exit code, which is the same nonzero for a conflict and for an oid we do not have. **It has a production caller now**: `choir-bridge queue --ci-command <file> --speculate` builds the round as a `MergeQueue` over `GitSpeculator`, checked by `WorktreeRunner`. That is the difference the seam was for, and it is a difference in what a pull request is told. The train path merges every open PR and asks CI once, so one red change makes every PR red and nothing lands; the queue tests each change against the state produced by the changes ahead of it -- "exactly as if they had been tested one at a time" -- so the green prefix lands, the blame is on the change that failed, and the window narrows. Ordering still goes through a sequencer, on an in-memory log: the queue records every landing through one, which is what keeps the single-writer order true of a train as well as of a push, but the forge is canonical here (D21) so the ordering of one round is not a claim anybody reads back, and writing a log would look like a second source of truth. `--speculate` is a field of the CI config rather than a flag beside it, because a per-change verdict needs an executor we drive: the forge answers about a ref, so asking it once per train member would be the same answer repeated under different names | Two-way |

| D18 | Nix-based CI with a shared remote build cache (L6). **The executor is a seam before it is a provider.** What ran a candidate merge was `fn verdict(&Change, &str) -> bool`, which was not a seam by this repository's own rule -- one implementation, no conformance suite, no second backend to disagree with it -- and stayed plausible only because synthetic closures always agreed. Three things the bool could not say, each of which changes a decision the queue makes. **A provider fault is not a test failure**: a VM that failed to boot and a test that legitimately failed both returned false, and the queue ejects on false, permanently, taking every change that transitively depends on the ejected one -- so our own outage rejected an agent's correct work and told it the work was wrong. `Verdict` has four cases and `Verdict::evicts` is the single place that rule lives, with only `Failed` saying yes; `Errored` and `TimedOut` stall the train instead, landing the green prefix, requeueing from the fault on, reporting `provider_error`, and leaving the window alone, since the window is the response to changes that fail and none of these did. **A batch is the unit**: the train's cost model assumes every member's CI runs in parallel while a one-job-at-a-time method taking `&mut self` made that impossible to implement, a wall-clock error of the batch size that synthetic verdicts returning instantly could never show, against D64's measured 199.8 ms of a 200 ms budget. Index alignment is the batch call's contract, and a provider returning the wrong count has attributed one change's result to another, so none are used. **A job is content-addressed**, because a queue-local change id does not survive being asked the same question twice. `LocalRunner` ships with the seam rather than after it: a conformance suite with one backend has never been tested against disagreement. The two backends prove different amounts and the suite says so -- LocalRunner runs real children and is evidence about exit codes, deadlines and start failures, Synthetic returns what it is told and corroborates only the protocol surface. A microVM executor is the third call to `conformance`. **The CREEP mitigation is a property of the job, not a deployment note**: whether artifacts may reach the shared cache is `Job::may_write_cache`, opt-in, false for untrusted and fork builds, because the failure mode of the safe default is a slow build and the failure mode of the other one is a poisoned artifact. Writing the test for `Job::cache_key`'s documented contract, which nothing had, found the collision it was meant to prevent living inside it: separator-byte framing made `["a", "b"]` and `["a\0b"]` hash identically, and a Rust String may contain a NUL, so anyone able to choose an argument could forge another command's key. Every field is length-prefixed now and counts frame the argv/environment boundary. `Job::label` carries what the content address cannot -- which change this is for -- and is deliberately outside the key, since two jobs testing byte-identical trees with the same command are the same work whichever change produced them, which is the case a shared cache exists to collapse. `CheckStatus::Errored` (D49) is the durable half, and the train now writes it: `set_check_reporter` makes the queue record *every* verdict as a `RecordCheck`, because the map from `Verdict` to `CheckStatus` is total and recording only the interesting ones would leave a reader unable to tell "it passed" from "nobody was reporting". An outage records the same reason against every subject in the refused batch, which is the case the whole chain was for -- a change whose CI never ran used to leave no trace at all. Off by default, like `set_journal`: the identity a check is reported under belongs to whoever runs the queue, and a default channel name would put an unattributable reporter into an ordered record. **Wiring it exposed that the queue's log was not a log.** Landings were submitted as the merged file bytes, an opaque payload nothing could fold, and one undecodable entry stops `View::materialize` -- so the first check op made the whole log unreadable. Landings are `SetWorkspaceHead` ops now, carrying the same content hash the job under test was keyed by, which is what lets a reader holding a workspace head ask what CI found about it. That defect was invisible for as long as `MergeQueue` was composed into nothing, which it still is. **The third conformance backend is the process boundary, not a VM.** Firecracker and Cloud Hypervisor both require KVM and this is a darwin machine, so a microVM executor written here would be the untested single implementation the seam exists to forbid; the part of it that carries the risk and *can* be gated is distance -- serialization, index alignment, and a far side that stops talking. `ProtocolRunner` spawns a helper and talks JSON lines; `choir-ci-local` is the reference helper and runs the batch with `LocalRunner`, so conformance compares in-process against out-of-process execution directly rather than testing a story about pipes. A KVM driver is a different helper behind the same three lines. A helper that dies mid-batch has its tail filled with `Errored` rather than returning a short list: the answers it gave are about the jobs it gave them for, and the queue refuses a miscount wholesale. **A job says where it runs, and that moved the protocol to 2.** `Job` could name a command but not a directory, so the seam could only run commands correct from any working directory, which is no build command at all -- the reason nothing with a checkout on disk could use it. `Job::directory` is `None` for a self-provisioning executor that materializes `Job::subject` itself and has no host path to be given, and `Some` for a caller that already has the tree on disk. The version moved for what reads as an additive field because a version-1 helper does not know the key: it runs the job wherever it happens to be and returns a verdict that is well-formed, index-aligned, and about the wrong tree, which is precisely the change a silent default survives. It is inside `Job::cache_key` while `Job::label` stays outside, the same test applied twice -- a label is not observable to the command and the working directory is, since toolchains write absolute paths into what they build, so two identical trees checked out at different paths can produce artifacts that differ, and one key over both is the CREEP false sharing `may_write_cache` bounds, reached from the honest direction rather than the malicious one. `None` and the empty path are distinct preimages, which a plain length-prefixed field would have collapsed. **The seam has a caller now, and it is the one that touches a real forge.** `MergeQueue` is still composed into nothing -- that has not changed -- but `choir-bridge`'s train, which is a separate implementation and the only one pointed at a live repository, takes its check verdict through `CiExecutor` when the operator gives it `--ci-command`. What that buys is not only exercise. The forge path has to publish the speculative merge of every open PR to a remote so that someone else's runners will look at it; `run_train_ci` checks the same train in the worktree that just built it, on a provider the operator picked, and nothing speculative leaves the machine. The two sources converge on one `green` flag before the landing decision, so neither gets its own landing rule, and the executor's own strings are held to the Rule of Two along with everything else: an `Errored` detail is printed for an operator and never interpolated into a commit status or read by a branch. A provider outage posts `error` rather than `failure`, which is the four-case `Verdict` finally reaching the place where telling an author their change is red because our VM fell over would have done the damage. Two things are deliberately not carried over: the `choir/train` branch is not pushed, having existed only so the forge would run CI, and the post-land watch is skipped, because a local executor tested exactly the commit that lands and a fast-forward makes the base tip that same tree -- there is no second, independent run to observe. The cost of that is stated rather than hidden: a nondeterministic failure the pre-land run missed now lands, where the forge path's second look would sometimes have caught it. **A batch is a batch of different trees, and the fourth backend is the one that acts like it.** `MergeQueue` tests every train member against its own speculative state, so handing a whole batch to a runner that works in one prepared directory tests the last state N times and answers under N different subjects -- well-formed, index-aligned, and wrong about everybody but the last. `Job::directory = None` already meant "the provider materializes the subject itself", written for a microVM and true of any repository holding the commit ids `GitSpeculator` produces. `worktree::WorktreeRunner` is that provider: `git worktree add --detach` per job, the command in that checkout, the checkout removed when the batch finishes. A job that *does* name a directory is run there untouched, because a caller who prepared a tree has said what they want. A subject it cannot check out is `Errored` and keeps its slot, never dropped and never `Failed`: a checkout we could not make is our fault. Cleanup goes through git's bookkeeping first and a plain delete second, because what sits at a checkout path is not always a worktree git knows about: its own are removed by the first, and the debris a crashed run left is a directory git has no record of, which the first refuses and the second deletes. That matters because `worktree add` refuses a path that exists, so without it one crash makes every later batch fault at provisioning -- reported as an outage, forever, until somebody cleans up by hand **A helper this workspace cannot build is gated by the same list, or it is not gated at all.** The conformance assertions lived only in `choir-queue/tests/it/executor.rs`, which reaches the backends cargo links and therefore every backend except the one the seam was carved out for: a KVM driver is written and run on a Linux machine, and a suite it cannot be pointed at gates nothing. They are `choir_queue::conform::conform` now, one copy, called by the in-tree suite and by `choir-ci-conform`, which takes the helper as an argv and exits nonzero on any failed check. It reports rather than panics, because a remote helper is usually wrong in more than one way at once and a suite that stops at the first assertion costs a round trip per defect -- with the handshake as the one exception, since nothing after it means anything and seven derived failures would name the wrong thing. A skipped check is printed as skipped and never counted as a pass: the `Job::directory` probe needs a directory the far side can see, which an isolation boundary ordinarily does not cross, and "unestablished" is the honest report. Usage errors exit 2 rather than 1, so a lane reading 1 as "the helper is wrong" is not told that by a typo in its own invocation | Two-way |

| D64 | Phase 1's absolute targets become measurements that can fail, and each is measured as the thing it can honestly be. The plan names four -- 5 commits/s/repo through the queue, green-keeping at 50 in-flight, 10k clones/hr, read p99 under 100 ms in-region -- and measured none: `choir-spike` is the *Phase-0* gate, `throughput.rs` reports the write path and deliberately asserts nothing, and nothing looked at reads at all. An unset gate is not a passed gate, which is the rule the withdrawn adoption criterion is already written down under; these had less excuse, because they existed and only needed instrumenting. | D77 | **A tripwire that scans other crates lives in a leaf crate that declares its subject.** Two invariants here hold by the *absence* of something -- an edge in the dependency graph (D40's replay purity), a type named in the wrong crate (D40's conflict quarantine) -- and one more, invariant 3's rule against unordered maps in hashed structs, holds over shapes nobody has written yet. None of the three can be asserted by exercising a value, so all three are checked by reading other crates as text. **A scanner's inputs are not its crate's inputs, and `gate` had no way to know that.** The gate decides two things from the crate a test lives in: whether the `touched` lane selects it, and whether a cached green verdict still stands. Both are computed from that crate's own files plus the dependency closure cargo reports. D40's quarantine sat in `choir-view` and read `choir-node`, which `choir-view` does not depend on and, by D40 itself, must not -- so editing `choir-node` neither selected the test nor invalidated its verdict, and the verdict cache would serve a green for a tree the scan had never read. Invariant 3's scanner sat in `choir-hash` and read every crate in the workspace, with the same blindness. **The obvious repairs are both worse.** Moving a scanner to the crate it scans does not generalize -- invariant 3 scans all of them -- and widening `choir-hash`'s inputs to the whole of `crates/` would invalidate every verdict in the workspace on every edit, because everything depends on `choir-hash`. Adding a dependency edge to make cargo see it is the edge D40 exists to forbid, and it would drag `choir-actor`'s tokio-and-libsqlite3 tree into the edit loop. **So the scanners get a crate of their own, and it is a leaf on purpose**: `choir-guards` depends on nothing and nothing depends on it, which is the property that lets its declared inputs name the entire workspace with the cost landing on that one crate. The declaration is `crates/choir-guards/gate-inputs`, one path per line, read by `compute_keys` and by `touched_pkgs`, and it is the only place another crate's `.rs` files enter a verdict key -- opt-in for exactly the reason the general exclusion exists, since a crate that declares a path is saying it is not a crate a leaf edit should leave alone. It is coarse by design, naming `crates/` rather than a file list, because a list is the thing that rots and the gate's own history has three separate entries about a list that was wrong. **The detector is not the invariant, and conflating them cost a day.** The quarantine scan was a substring search over raw file text, so it fired on `browse.rs:2305` -- a rustdoc link in the comment explaining *why* a committed conflict is rendered from git's markers rather than from choir's own type. That is the comment most worth linking, and reading it as an opened one-way door failed `main`. The scan now runs over `strip_comments`, so prose may name a quarantined type and code may not, and `the_scanner_reads_code_and_not_prose` pins that distinction in both directions on synthetic sources -- because a source scanner is the classic vacuous test, and loosening a detector must not be able to become loosening an invariant by accident. **The width and the narrowness are both tested.** `the_cache_key_follows_the_files_that_produced_it` already held that a key is not too wide; `a_guard_crates_key_follows_the_sources_it_scans` holds that it is not too narrow, asserting both halves -- the verdict invalidated *and* the lane selecting the crate -- and carrying its own fixture into the throwaway worktree so it cannot pass vacuously on a tree with no guard crate in it | Two-way |

## Reading the door column

- **Two-way** — reversible by deleting code. No persisted format, op, hash or
  signature is involved, so reversing leaves nothing to migrate.
- **One-way** — the choice is baked into bytes that already exist. Reversing it
  means migrating persisted data.
- **One-way for readers** — the feature can stop being *written* at any time and
  nothing breaks, but the log is append-only, so the first accepted entry of
  that shape permanently ends replay compatibility with earlier binaries.
- **Gated** — deliberately deferred, with the swap planned rather than assumed.
